# PNCW v0.2 GCM-Guided Projection Planning — Normative Execution Clarifications

**Status:** Normative companion to `2026-08-30-pncw-v0.2-gcm-guided-projection-planning.md`  
**Spec:** `../specs/2026-08-30-pncw-v0.2-gcm-guided-projection-planning-design.md`

These clarifications resolve implementation-level ambiguity without changing the approved v0.2 architecture.

## 1. Digest Domains

Do not infer ownership from a field name ending in `Digest`.

### PNCW-owned canonical digests

The following are recomputed by PNCW using the PNCW canonical JSON/hash rules and use the `sha256:<64 lowercase hex>` form:

```text
candidate semantic digest
candidateSetDigest
budgetDigest
policyDigest
frozenInputDigest
selectedCandidateDigest
planSnapshotDigest
conformanceDigest
gcmPlanDigest in ProjectionPlanningReceipt (because it equals PNCW planSnapshotDigest)
```

CID/BID/PPRID/PPID use their documented `pncw:*:<64 lowercase hex>` prefixes.

### GCM-native opaque identities

The following are preserved as non-empty opaque GCM identities and MUST NOT be rewritten, re-prefixed, or rehashed merely to look like PNCW digests:

```text
snapshotDigest
gcmPlanningAuthorityDigest
GcmConformanceIdentityV1.profileDigest
allocationPlanDigest
policySelectionDigest
resourceSnapshotDigest in the real-adapter snapshot registry
GCM replan lineage references
```

PNCW may hash these opaque strings as inputs to FID/GPD/PPID, but the original GCM value remains evidence.

Schemas for GCM-native opaque fields require bounded non-empty strings and reject control characters; they do not impose the PNCW `sha256:` pattern unless the actually supported GCM public profile explicitly guarantees that syntax.

## 2. Canonical Decimal Comparison

`compareCanonicalDecimal()` is exact BigInt arithmetic, not a lexical comparison and not a float conversion.

Normative algorithm:

```ts
export interface DecimalParts {
  sign:-1|0|1
  coefficient:bigint
  scale:number
}

export function parseCanonicalDecimal(value:CanonicalDecimalV1):DecimalParts {
  assertCanonicalDecimal(value)
  const negative=value.startsWith('-')
  const body=negative?value.slice(1):value
  const [whole,fraction='']=body.split('.')
  const coefficient=BigInt(`${whole}${fraction}`)
  if(coefficient===0n) return {sign:0,coefficient:0n,scale:fraction.length}
  return {sign:negative?-1:1,coefficient,scale:fraction.length}
}

function scaled(parts:DecimalParts,targetScale:number):bigint {
  return BigInt(parts.sign)*parts.coefficient*10n**BigInt(targetScale-parts.scale)
}

export function compareCanonicalDecimal(
  left:CanonicalDecimalV1,
  right:CanonicalDecimalV1,
):-1|0|1 {
  const a=parseCanonicalDecimal(left)
  const b=parseCanonicalDecimal(right)
  const scale=Math.max(a.scale,b.scale)
  const av=scaled(a,scale)
  const bv=scaled(b,scale)
  return av<bv?-1:av>bv?1:0
}
```

No identity-bearing planning calculation may call `Number()`, `parseFloat()`, or equivalent before canonical identity is fixed.

## 3. Parent and Child Planning Request Identity During Replan

`ProjectionReplanRequestV1.planningRequestId` names the parent/original planning request associated with `parentPlanningId`.

A fresh replan uses a new `ProjectionPlanningRequestV1` whose `frozenInputRef` equals `ProjectionReplanRequestV1.newFrozenInputRef`.

Therefore:

```text
parent receipt.planningRequestId = parent PPRID
replanRequest.planningRequestId  = parent PPRID
new planning request ID          = child PPRID derived from new FID
```

The child PPRID is never overwritten with the parent PPRID. Parent/child relation is lineage, not identity reuse.

## 4. Real GCM Phase-B B2 Snapshot Reconstruction

`planningClass` is PNCW-opaque. The real adapter resolves it through configured `routeProfiles` to GCM-native executor/configuration/capability requirements.

`FrozenPlanningInputRefV1.snapshotRef` resolves through the adapter-local `snapshotRegistryPath`. A registry entry contains pinned GCM-native World/Foundation/Authority locators and the public `ResourceRecord` inputs needed to reconstruct a B2 resource snapshot.

The Python host must first freeze an installed-wheel public API profile containing at least:

```text
ResourceRecord
ResourceProvider
StaticResourceProvider
ResourceInventory
ResourceInventorySnapshot
AllocationTask
AllocationCandidate
AllocationRequest
AllocationPlan
AllocationSearchLimits
Allocator0.allocate
build_allocation_candidates
build_allocation_request
validate_allocation_handoff
FeasiblePlanEnumerator.enumerate
compute_pareto_frontier
select_from_frontier
LexicographicPolicy
WeightedLinearPolicy
ReplanRequest
ReplanningCoordinator.replan
```

It then reconstructs the pinned `ResourceInventorySnapshot` only through that frozen public construction/binding surface and verifies the resulting resource snapshot identity against the registry's pinned identity before planning.

If the installed wheel does not expose a sufficient public B2 construction/reconstruction path, the real adapter validation stops with an interoperability defect. Private imports are forbidden as a workaround.

## 5. Authority Boundary

GCM-native `authority_ref` / `gcmPlanningAuthorityDigest` may participate only in GCM's own candidate admissibility and frozen allocation semantics.

They MUST NOT be translated into:

```text
AuthorityContextV1
sourceRead
surfaceProject
visibility authority
commit authority
writer capability
```

The current PNCW caller authority enters only at `ProjectionRequestCompiler`, after plan acceptance, and is independently rechecked by the sealed v0.1.0 Readiness/Verification path.

## 6. Evidence Rule

Real GCM wheel SKIP, real HDSRC SKIP, or real full-E2E SKIP is visible missing evidence. It is never converted to a conformance PASS.

A v0.2 release-candidate seal requires the design's AC01–AC18 to be executable PASS, including actual installed GCM Phase-B and actual GCM→HDSRC/MRMIC→PNCW evidence.
